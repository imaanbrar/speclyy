# ADR-0008: ORM — Drizzle

- **Status:** Accepted
- **Date:** 2026-04-20

## Context

We need a query layer between the Next.js app and Postgres on Supabase. Requirements:

- Full TypeScript type safety on queries and results
- Schema definition and migration management
- Compatible with Next.js App Router (RSC, Server Actions, edge runtime)
- Works alongside the Supabase JS client (which handles user-facing queries with RLS via JWT)
- Supports Postgres-specific features used in our schema (`GENERATED ALWAYS AS`, partial indexes, JSONB)
- Low friction for a developer with strong SQL background

## Decision

Use **Drizzle ORM** with **Drizzle Kit** for schema definition and migrations.

### Usage pattern

Drizzle is used for **internal/service queries** — Stripe webhook handlers, background jobs, admin operations, and any query running under the service role. User-facing queries in RSC and Server Actions continue to use the **Supabase JS client** (`createServerClient`) which carries the user's JWT and enforces RLS automatically.

```ts
// Schema — TypeScript, code-first
export const profiles = pgTable('profiles', {
  id: uuid('id').primaryKey().references(() => authUsers.id),
  firstName: text('first_name'),
  lastName: text('last_name'),
  studioName: text('studio_name'),
  market: text('market'),
  onboardingCompletedAt: timestamptz('onboarding_completed_at'),
  isOnboarded: boolean('is_onboarded').generatedAlwaysAs(
    sql`onboarding_completed_at IS NOT NULL`
  ).stored(),
  createdAt: timestamptz('created_at').notNull().defaultNow(),
  updatedAt: timestamptz('updated_at').notNull().defaultNow(),
})

// Query — mirrors SQL, fully typed
const groups = await db
  .select()
  .from(projectGroups)
  .where(eq(projectGroups.projectId, projectId))
  .orderBy(asc(projectGroups.position))
```

### Migration workflow

```bash
# Generate migration after schema change
drizzle-kit generate

# Review the produced .sql file, then apply
drizzle-kit migrate
```

Migrations are readable SQL files committed to the repo. Each is reviewed before it runs.

## Rationale

**SQL-forward maps to existing instincts.** The query builder is a direct TypeScript representation of SQL — `select`, `from`, `where`, `join`, `orderBy` are explicit. A developer who knows Postgres reads Drizzle queries and immediately understands what runs. No new abstraction model to learn.

**No codegen step.** Types are inferred at compile time from the schema definition. There is no `prisma generate` to run after each schema change, no generated client to commit, and no CI step that fails because someone forgot to regenerate. Schema change → TypeScript types update automatically.

**Migrations are auditable SQL.** `drizzle-kit generate` produces a `.sql` file you read and approve before applying. Given we're running a financial product with user data, knowing exactly what DDL runs on production matters.

**Native `GENERATED ALWAYS AS` support.** Our `is_onboarded` column is a Postgres generated column (`GENERATED ALWAYS AS (onboarding_completed_at IS NOT NULL) STORED`). Drizzle models this directly in the schema definition. Prisma has no native support for generated columns — it would require raw SQL workarounds and hiding the column from the Prisma model.

**Lightweight, edge-compatible.** ~30KB bundle, no native binary, runs on Node and edge runtimes. Prisma ships ~300KB+ and requires a query engine binary that is not edge-compatible without additional configuration.

**Clean dual-client pattern with Supabase.** Supabase JS client carries the user JWT and enforces RLS for user-facing queries. Drizzle connects via the service-role Postgres URL for internal operations where RLS should be bypassed (Stripe webhooks, background jobs). The two clients serve different purposes and do not conflict.

## Consequences

**Positive**
- Query intent is immediately readable — no mental translation from ORM abstraction to SQL.
- Zero codegen step removes a class of "forgot to regenerate" bugs.
- Migrations as reviewed SQL files fit the mental model of a developer with RDS/Postgres experience.
- Full type inference — return types are structural, not nominal, so IDE autocomplete is precise.
- Postgres-specific features (JSONB operators, generated columns, partial indexes) are first-class.

**Negative**
- Drizzle is younger than Prisma — less StackOverflow coverage, occasional API roughness.
- Relational query API (`.relational`) is newer and slightly more verbose than Prisma's `include` for deeply nested reads.
- If a future hire is Prisma-fluent, there is a ramp-up period.

## Alternatives considered

- **Prisma** — Mature, excellent docs, ergonomic nested reads. Rejected because: (a) requires `prisma generate` codegen step after each schema change; (b) 300KB+ bundle, not edge-compatible; (c) no native `GENERATED ALWAYS AS` support — our `is_onboarded` column requires raw SQL workaround; (d) auto-generated migration SQL is harder to audit than Drizzle's explicit SQL files; (e) RLS interaction requires manually setting JWT claims via `$executeRaw` per query, not the happy path. Revisit if team grows and Prisma fluency is a hiring advantage.
- **Kysely** — Excellent type-safe query builder, edge-compatible, no schema or migrations. Rejected because lack of schema definition means migrations need a separate tool and schema-to-type drift is possible. Drizzle subsumes Kysely's strengths with added schema management.
- **Raw SQL via `postgres.js`** — Full control, no abstraction, extremely mature. Rejected because no compile-time type safety on query results — return types are `any` without manual annotation. Acceptable for one-off scripts; too risky for a production query layer.
