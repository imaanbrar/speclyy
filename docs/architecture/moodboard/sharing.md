# Sharing & comments

Two share modes coexist: **studio-team read/write** (via org membership) and **public client read-only with comments** (via signed share tokens).

See [README.md](README.md) for the broader moodboard architecture and [board-persistence.md](board-persistence.md) for the document model these views render.

---

## The two modes at a glance

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                   │
│  Mode A — Studio team (signed-in)                                 │
│  ───────────────────────────────────                              │
│  Path:    moodboard.speclyy.com/board/[id]                        │
│  Auth:    Supabase session cookie (.speclyy.com)                  │
│  Access:  read + write, full studio shell                         │
│  Comes from: organization_members.user_id = auth.uid()            │
│              AND organizations.id = boards.org_id                 │
│  RLS:     enforced (boards.owner_id OR boards.org_id ∈ my orgs)   │
│                                                                   │
│  ────────────────────────────────────────────────────────────     │
│                                                                   │
│  Mode B — Client (public, token URL)                              │
│  ───────────────────────────────────                              │
│  Path:    moodboard.speclyy.com/share/[token]                     │
│  Auth:    none — token in URL is the credential                   │
│  Access:  view-only OR view + comment                             │
│  Comes from: board_shares.token = $token AND not revoked/expired  │
│  RLS:     bypassed by service-role Route Handler;                 │
│           handler returns a redacted document.                    │
│                                                                   │
└──────────────────────────────────────────────────────────────────┘
```

## Org-scoped read/write (Mode A)

The existing `organizations` and `organization_members` tables (per [auth.md](../auth.md)) own studio membership. Boards have an optional `org_id`:

- `org_id IS NULL` → solo board, only the owner sees it.
- `org_id = X` → all members of org X read and write.

RLS for studio members:

```sql
CREATE POLICY boards_org_members ON public.boards FOR ALL
  USING (
    org_id IS NOT NULL
    AND org_id IN (
      SELECT organization_id FROM public.organization_members WHERE user_id = auth.uid()
    )
  )
  WITH CHECK (
    org_id IS NOT NULL
    AND org_id IN (
      SELECT organization_id FROM public.organization_members WHERE user_id = auth.uid()
    )
  );
```

A designer creating a board picks the org in the studio shell (or it's defaulted to their primary org if they have one). Promoting a solo board to an org board is a single `UPDATE`.

Comments authored by signed-in members are tagged `author_user = auth.uid()`; their display name and avatar come from `profiles`.

## Public share tokens (Mode B)

```sql
CREATE TABLE public.board_shares (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  board_id    uuid NOT NULL REFERENCES public.boards(id) ON DELETE CASCADE,
  token       text UNIQUE NOT NULL,                   -- 32-byte url-safe random
  access      text NOT NULL CHECK (access IN ('view','comment')),
  expires_at  timestamptz,                            -- null = never
  revoked_at  timestamptz,
  created_by  uuid NOT NULL REFERENCES public.profiles(id),
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

Generated by a Server Action when the designer clicks "Share with client":

```ts
'use server'
export async function createShareLink(boardId: string, opts: { access: 'view' | 'comment'; expiresInDays?: number }) {
  await assertBoardWritable(boardId)
  const token = randomBytes(32).toString('base64url')
  await db.insert(boardShares).values({
    boardId, token, access: opts.access,
    expiresAt: opts.expiresInDays ? add(new Date(), { days: opts.expiresInDays }) : null,
    createdBy: userId,
  })
  return `https://moodboard.speclyy.com/share/${token}`
}
```

**The token *is* the credential.** Anyone with the URL can view (or comment). The designer can revoke at any time (sets `revoked_at`).

### The public Route Handler

`/share/[token]` is **not** a regular Next.js page. It's a Route Handler that:

1. Looks up the token, checks `revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now())`.
2. Fetches the board with the **service-role** client (RLS bypassed).
3. Returns a redacted document — strips `owner_id`, `org_id`, `author_user`, internal item refs that the client shouldn't see.
4. Renders the studio shell in **read-only** mode, with a comment composer enabled if `access = 'comment'`.

```ts
// apps/moodboard/src/app/share/[token]/page.tsx
export default async function SharePage({ params }: { params: { token: string } }) {
  const share = await dbServiceRole.query.boardShares.findFirst({
    where: and(eq(boardShares.token, params.token), isNull(boardShares.revokedAt), gtOrNull(boardShares.expiresAt, new Date())),
  })
  if (!share) notFound()

  const board = await dbServiceRole.query.boards.findFirst({
    where: eq(boards.id, share.boardId),
  })
  return <ReadOnlyStudio board={redactBoard(board)} share={share} />
}
```

### Why service-role + redaction (not anonymous RLS)

A "view via token" RLS policy on `boards` would require the token to be passed through a JWT claim — Supabase Auth doesn't natively model unauth-but-scoped sessions. The Route-Handler pattern is simpler, has clearer audit logs, and keeps RLS uniformly "auth.uid()"-shaped for everything else.

## Comments

```sql
CREATE TABLE public.board_comments (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  board_id    uuid NOT NULL REFERENCES public.boards(id) ON DELETE CASCADE,
  parent_id   uuid REFERENCES public.board_comments(id),  -- threaded
  item_id     text,                                       -- doc-tree item id, optional
  author_user uuid REFERENCES public.profiles(id),        -- one of these two
  share_id    uuid REFERENCES public.board_shares(id),    -- is non-null
  author_name text,                                       -- shown when share_id-authored
  body        text NOT NULL,
  resolved_at timestamptz,
  created_at  timestamptz NOT NULL DEFAULT now(),
  CHECK (
    (author_user IS NOT NULL AND share_id IS NULL) OR
    (author_user IS NULL     AND share_id IS NOT NULL AND author_name IS NOT NULL)
  )
);
```

Two authoring paths:

| Author | How | Display |
|---|---|---|
| Studio member | Signed-in Server Action; `author_user = auth.uid()` | Avatar + profile name |
| Anonymous client | Public POST against `/share/[token]/comment`, requires `access = 'comment'`, `author_name` provided in body | Initials + name they typed; "via share link" tag |

Comments are pinned to the board overall (`item_id IS NULL`) or to a specific item (`item_id = '<doc-tree id>'`). Pinning to an item id keeps comments stable across drag/resize/rotate — the item id doesn't change when its frame does.

### RLS for comments

```sql
ALTER TABLE public.board_comments ENABLE ROW LEVEL SECURITY;

-- read: anyone who can read the board can read its comments
CREATE POLICY board_comments_read ON public.board_comments FOR SELECT
  USING (board_id IN (SELECT id FROM public.boards));    -- piggybacks on boards RLS

-- write (signed-in): own row, on a board they can read
CREATE POLICY board_comments_write_self ON public.board_comments FOR INSERT
  WITH CHECK (author_user = auth.uid());
```

Anonymous comments (`share_id IS NOT NULL`) are inserted by the public Route Handler with the **service-role** client, after validating the token has `access = 'comment'`. They never touch RLS.

### Anti-abuse on anonymous comments

- Per-share rate limit (e.g. 20 comments / 5 min) tracked in a small `share_id → window` Redis-style table or via Inngest event-driven counter.
- Body length cap (4 KB).
- Optional CAPTCHA gate after N comments per share.
- The board owner can revoke a share with one click; revoking nukes the link without losing existing comments (they're tied to `share_id`, which remains).

## Notification model (light)

When a comment is posted to a board:

1. `board_comments` insert fires an `Inngest` event `board/comment.posted`.
2. The Inngest function emails the board owner + any prior commenters (deduped, batched on a 2-minute window).

This is the only place comments touch external services. Email is sent via the existing transactional path. Real-time in-app notifications are deferred.

## UI — designer's share panel

```
┌───────────────────────────────────────────────┐
│ Share this board                              │
├───────────────────────────────────────────────┤
│  Studio team — Verdant Atelier                │
│  ▸ 4 members · read & write                   │
│                                               │
│  Public link                                  │
│  ▸ moodboard.speclyy.com/share/aZ9k…  [Copy]  │
│    Access:  ◉ View   ◯ View + comment         │
│    Expires: ◯ Never  ◉ In 30 days             │
│    [Revoke link]                              │
│                                               │
│  Comments (5 unresolved)                      │
└───────────────────────────────────────────────┘
```

A board has one active link per access level (`view`, `comment`). Creating a new one auto-revokes the prior link of that level. This keeps the model clean: at most two live URLs per board.
